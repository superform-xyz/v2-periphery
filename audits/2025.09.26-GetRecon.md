# H-01 `ERC7540YieldSourceOracle` is discounting assets for which `requestRedeem` is being called

## Impact

`ERC7540YieldSourceOracle.getTVLByOwnerOfShares` looks as follows:

https://github.com/superform-xyz/v2-core/blob/fcce91733c1fa9c63dc8bb3b1c9a75930fd65003/src/accounting/oracles/ERC7540YieldSourceOracle.sol#L75-L88

```solidity
    /// @inheritdoc AbstractYieldSourceOracle
    function getTVLByOwnerOfShares(
        address yieldSourceAddress,
        address ownerOfShares
    )
        public
        view
        override
        returns (uint256)
    {
        uint256 shares = IERC20(IERC7540(yieldSourceAddress).share()).balanceOf(ownerOfShares);
        if (shares == 0) return 0;
        return IERC7540(yieldSourceAddress).convertToAssets(shares);
    }
```

This is estimating the TVL controller by `ownerOfShares`

But because ERC7540 is asynchronous, the TVL can also include assets that can be claimed via `redeem` / `withdraw`, in the case of Centrifuge V3, the assets are exactly `maxWithdraw`.

Additionally shares that have yet to be redeemed, will be moved to the escrow.

## POC

The following POC is highly speculative as I don't have context on how this function will be used

- Have X assets
- Queue a withdrawal on the ERC7540
- Assets depress since the `getTVLByOwnerOfShares` will underestimate the assets (the shares are in the escrow)
- Redemption is fulfilled on centrifuge side
- Assets are now in `maxWithdraw` but the `getTVLByOwnerOfShares` return value is still depressed
- New deposits will be able to mint shares at this depressed price (assuming `getTVLByOwnerOfShares` is involved in how PPS is computed)

## Mitigation

The ERC7540 oracle will have to be vault specific
And will have to account for requested redemptions
As well as redemptions fulfilled

# H-02 `ERC7540YieldSourceOracle` is not pricing the `SuperVaultStrategy` shares, causing it to be unable to withdraw the correct amount of assets

## Impact

`_processSingleFulfillHookExecution` will use `getShareOutput` from the `IYieldSourceOracle` to determine how many shares to withdraw from the target

https://github.com/superform-xyz/v2-periphery/blob/abbf22cd06a7c508dc2cf2974208fb0aeec61ed2/src/SuperVault/SuperVaultStrategy.sol#L666-L673

```solidity
        // Calculate underlying shares and update hook calldata
        vars.amountOfAssets = vars.superVaultShares.mulDiv(currentPPS, PRECISION, Math.Rounding.Floor);
        vars.svAsset = address(_asset); /// @audit Centrifuge Grief / Mistake based on how the oracle is implemented?
        vars.amountConvertedToUnderlyingShares = IYieldSourceOracle(yieldSources[vars.targetedYieldSource])
            .getShareOutput(vars.targetedYieldSource, vars.svAsset, vars.amountOfAssets);
        hookCalldata =
            ISuperHookOutflow(hook).replaceCalldataAmount(hookCalldata, vars.amountConvertedToUnderlyingShares);
```

In the case of ERC7540, the implementation for the `ERC7540YieldSourceOracle` is the following:

https://github.com/superform-xyz/v2-core/blob/dev/src/accounting/oracles/ERC7540YieldSourceOracle.sol

```solidity
    /// @inheritdoc AbstractYieldSourceOracle
    function getShareOutput(
        address yieldSourceAddress,
        address,
        uint256 assetsIn
    )
        external
        view
        override
        returns (uint256)
    {
        return IERC7540(yieldSourceAddress).convertToShares(assetsIn);
    }
```

In the case of Centrifuge V3, `convertToShares` will use the Global Price that the vault has:
https://github.com/centrifuge/protocol-v3/blob/4f69794392c44cdbf6d27121fd37a2c6ec9eeced/src/vaults/SyncManager.sol#L160-L178

```solidity
    /// @inheritdoc ISyncManager
    function convertToShares(IBaseVault vault_, uint256 assets) public view returns (uint256 shares) {
        VaultDetails memory vaultDetails = spoke.vaultDetails(vault_);

        D18 poolPerShare = pricePoolPerShare(vault_.poolId(), vault_.scId());
        D18 poolPerAsset = spoke.pricePoolPerAsset(vault_.poolId(), vault_.scId(), vaultDetails.assetId, true);

        return poolPerShare.isZero()
            ? 0
            : PricingLib.assetToShareAmount(
                vault_.share(),
                vaultDetails.asset,
                vaultDetails.tokenId,
                assets.toUint128(),
                poolPerAsset,
                poolPerShare,
                MathLib.Rounding.Down
            );
    }

```

Whereas when performing a redemption/withdrawal, the Centrifuge `AsyncRequestManager` will use the `state.redeemPrice` which is custom for each controller (in the case the `SuperVaultStrategy`)

https://github.com/centrifuge/protocol-v3/blob/4f69794392c44cdbf6d27121fd37a2c6ec9eeced/src/vaults/AsyncRequestManager.sol#L368-L397

```solidity
/// @inheritdoc IRedeemManager
    function redeem(IBaseVault vault_, uint256 shares, address receiver, address controller)
        public
        auth
        returns (uint256 assets)
    {
        _checkIsLinked(vault_);
        require(shares <= maxRedeem(vault_, controller), ExceedsMaxRedeem());

        AsyncInvestmentState storage state = investments[vault_][controller];

        uint128 assetsUp = _shareToAssetAmount(vault_, shares.toUint128(), state.redeemPrice, MathLib.Rounding.Up);
        uint128 assetsDown = _shareToAssetAmount(vault_, shares.toUint128(), state.redeemPrice, MathLib.Rounding.Down);
        _processRedeem(state, assetsUp, assetsDown, vault_, receiver, controller);
        assets = uint256(assetsDown);
    }

    /// @inheritdoc IRedeemManager
    function withdraw(IBaseVault vault_, uint256 assets, address receiver, address controller)
        public
        auth
        returns (uint256 shares)
    {
        _checkIsLinked(vault_);

        AsyncInvestmentState storage state = investments[vault_][controller];
        uint128 assets_ = assets.toUint128();
        _processRedeem(state, assets_, assets_, vault_, receiver, controller);

        shares = uint256(_assetToShareAmount(vault_, assets_, state.redeemPrice, MathLib.Rounding.Up));
    }
```

This will break the accounting having the following impacts:


## POC

### When the PPS of the Centrifuge Vault is higher

- Withdraws less shares than the price that the SuperVaultStrategy has for it's withdrawals
- Causes direct losses to withdrawers

### When the PPS of the Centrifuge Vault is lower

- Withdraws too many shares
- Causes a direct loss to the SuperVaultStrategy
- Can revert due to attempting to withdraw more than the shares available

Note that the total shares available for withdrawal/redemption is a virtual number computed by using maxWithdraw and  `state.redeemPrice` meaning an additional rounding factor has to be taken into account.

## Mitigation

You likely will have to write a specific oracle for each target (as each ERC7540 will have a different way of storing withdrawal prices)
And make sure to use the correct price.

In this case you'll need to compute the shares by using:

```solidity
mapping(IBaseVault vault => mapping(address investor => AsyncInvestmentState)) public investments;
```

with the formula:

```solidity
    function _assetToShareAmount(IBaseVault vault_, uint128 assets, D18 priceAssetPerShare, MathLib.Rounding rounding)
        internal
        view
        returns (uint128 shares)
    {
        VaultDetails memory vaultDetails = spoke.vaultDetails(vault_);
        address shareToken = vault_.share();

        return priceAssetPerShare.isZero()
            ? 0
            : PricingLib.assetToShareAmount(
                shareToken, vaultDetails.asset, vaultDetails.tokenId, assets, priceAssetPerShare, rounding
            );
    }
```

Applying rounding down as to cause the slight loss to the recipient instead of the `SuperVaultStrategy`

# H-03 `manager` can escape slashing since `withdrawStake` has no cooldown

## Impact

At this time it seems that slashing is not available since `slashStake` cannot be called.

However, the design of the code allows to escape a slashing

Since `withdrawStake` has no delay

https://github.com/superform-xyz/v2-periphery/blob/3e58774e1acbc970b318b10c9aca529fad325421/src/SuperVault/SuperVaultAggregator.sol#L402-L423

```solidity

    function withdrawStake(uint256 amount) external {
        if (amount == 0) revert ZERO_ADDRESS(); // Reusing error code for consistency

        // Check sufficient balance
        if (_managerStakeBalance[msg.sender] < amount) {
            revert INSUFFICIENT_STAKE_BALANCE();
        }

        // Get the UP token address from SUPER_GOVERNOR
        address upToken = SUPER_GOVERNOR.getAddress(SUPER_GOVERNOR.UP());

        // Update stake balance
        unchecked {
            _managerStakeBalance[msg.sender] -= amount;
        }

        // Transfer UP tokens to manager
        IERC20(upToken).safeTransfer(msg.sender, amount);

        emit StakeWithdrawn(msg.sender, amount);
    }
```

A manager that is about to get slashed can simply call `withdrawStake` to avoid getting slashed

## Mitigation

`withdrawStake` should be behind a timelock that allows the governor to perform slashing, if `slashStake` will have a delay then the delay for `withdrawStake` must be long enough to allow slashing

Additionally, stake that is queued for withdrawal should no longer be considered valid as otherwise a manager could simply queue a withdrawal so that they have the ability to evade slashing while retaining their stake

# M-01 ERC4626YieldOracle `getShareOutput` will return the wrong value for a redemption when the vault charges a fee on deposit and not on redemption

## Impact

The function `getShareOutput` in `ERC4626YieldOracle` looks as follows:

https://github.com/superform-xyz/v2-core/blob/fcce91733c1fa9c63dc8bb3b1c9a75930fd65003/src/accounting/oracles/ERC4626YieldSourceOracle.sol#L25-L37

```solidity
    /// @inheritdoc AbstractYieldSourceOracle
    function getShareOutput(
        address yieldSourceAddress,
        address,
        uint256 assetsIn
    )
        external
        view
        override
        returns (uint256)
    {
        return IERC4626(yieldSourceAddress).previewDeposit(assetsIn);
    }
```

This is using `previewDeposit` which in a ERC4626 compliant vault will include fees and possible slippage.

The function is used to determine how many shares to redeem from the underlying vault

https://github.com/superform-xyz/v2-periphery/blob/597f98364b10863c87acb43d689ab932856777d8/src/SuperVault/SuperVaultStrategy.sol#L629-L634

```solidity
        vars.amountOfAssets = IERC4626(_vault).convertToAssets(vars.superVaultShares);
        vars.svAsset = address(_asset);
        vars.amountConvertedToUnderlyingShares = IYieldSourceOracle(yieldSources[vars.targetedYieldSource])
            .getShareOutput(vars.targetedYieldSource, vars.svAsset, vars.amountOfAssets);
        hookCalldata =
            ISuperHookOutflow(hook).replaceCalldataAmount(hookCalldata, vars.amountConvertedToUnderlyingShares);
```

So, when `deposit` of the underlying vault has a fee, but redeeming doesn't this will cause a loss to the `controller`, although no loss has happened.

## Mitigation

You should review each Vault integration and ensure that non of these gotchas are possible.
I believe that for Euler, Morpho and Yearn, this risk is not present

# M-02 Sandwhiching a step-wise Oracle Update will cause losses to next depositor if they deposit while the PPS is incorrectly overstated

## Impact

As discussed by the Superform Team: https://www.notion.so/superform/MEV-Protection-Research-and-Discuss-Approach-27e35672200c806a9535ecdd5efefdc2 and discussed in this review, a deposit can sandwhich an oracle update, to steal the yield.

Doing that has an additional side effect, the PPS will be overstated.

Depositing against that overstated PPS will cause losses to depositors.

The losses will be permanent until the PPS is updated to accurately reflect the ratio between the Assets and the Shares.

## POC

-> Assume the Vault has a 1 to 1 (1e18 PPS
-> Deposits will receive 1 to 1 shares for assets
-> Say we will have a drastic improvement in the PPS, to 1.5
-> MEV Actor frontruns the update, the "real" PPS should be 1.25. But onchain we have 2x the shares at 1.5 PPS (overstated PPS)
-> Victim deposits at 1.5, they are overpaying by (1.5 / 1.25 = 20%), they do not lock in any losses now as the PPS is still 1.5
-> The PPS is updated to 1.25, which should have been the correct ratio (arguably the PPS may be different if we account for the assets / shares of victim, but that is beside the point). Victim has locked in a 20% loss through no fault of their own

## Mitigation

Any time the update to the PPS will be small, this should not be an issue.

However, at times where the PPS will update significantly, it may be necessary to ensure that the vault was not sandwhiched, perhaps by performing a onchain check of the total assets of the vault + strategy.

An alternative fix is to vest these changes over time.

Another plausible alternative is that if a PPS update will cause spikes, you could temporarily raise the minting fees until the Price has updated.

## 3 sources of losses to the vault

- Normal Loss from Vaults | Should be socialized

Whenever a user calls `Vault.withdraw` most (safe) ERC4626 will roundUp the amount of shares to burn. This typically causes 1 (wei) share to be lost by the caller. It's worth noting that for integrations that are step-wise in nature (e.g. ERC7540 that pay a premium every month, strategies that have to claim assets and compound them every X days without linear vesting), this attack can become highly profitable.

Due to this it's critical that PPS updates are as smooth as possible.

## POC

Invariant testing demonstrates the issue, the naive PPS decreases when a deposit happens, because the actual underlying assets are being socialized to new depositors due to using a hardcoded PPS

```solidity

## Mitigation

Yield updates should be vested over some time, this can be enforced offchain by having gradual updates to the PPS.

Additionally minting fees should be set to be higher than the average oracle update deviation to nullify the benefit of frontrunning

        if (processedShares + TOLERANCE_CONSTANT < totalRequestedAmount) {
            revert INVALID_REDEEM_FILL();
        }
```

Means that for each controller, the manager has to redeem 100% of their shares, minus a small constant.

This means that any controller can grief the processing of redemptions by asking to redeem a few more shares, or by cancelling and performing a new request with a slightly lower amount.

## Mitigation

I believe this should be accepted as is, with the possibility of delaying / refusing to redeem griefers.

Adding partial redemptions could be good for other reasons, but must be done only once the redemption mechanism is cognizant of losses during the withdrawal of underlying assets

2. If an admin fulfills a redemption at a high price it can lock in insolvency. See the issue [here](https://github.com/Recon-Fuzz/superform-review/issues/67)

## Preamble

Moving shares accumulators has an inherent rounding error:

```solidity

        uint256 movedCostBasis = sharesToMove == availableAccumulatorShares
            ? fromState.accumulatorCostBasis
            : Math.mulDiv(
                sharesToMove,

                availableAccumulatorShares,
                Math.Rounding.Floor
            );
```

I'm trying to escalate this to weaponize it, the goal being to perform small transfers of tokens

## Current conclusion

Rounding can be used to distribute the remainder (spread over multiples in the mantissa) as to effectively transfer a lower ratio (higher fees) to the recipient, this makes the ratio of Basis/Shares move upwards to the next integer, once it does, rounding will no longer be relevant (when Basis/Shares reaches a new integer all remainders are 0).

This leads me to conclude that the maximum impact is at most gaining 1 wei of basis (paying 1 wei less of fees) and sending 1 wei more of fees to the recipient.

Which is a very low impact.

## Math Intuition

Assume the costBasis / Shares is 3.25

Rounding will cause 3 to be moved
Moving 3 means that the .25 is kept

We reduce the basis of the caller by 3 and add 3 to the basis of the recipient
We should instead add 3.25

This causes the basis / shares of the sender to increase

As we repeat this the ratio of basis/shares for the sender increases to 4

Once it hits 4, we have no rounding, so we can no longer weaponize it

# A-01 Tokens for which a insolvency tollerance may be necessary

In many parts of the code, the constant `TOLERANCE_CONSTANT` is used.

This should never be necessary when it comes to shares, as all math should be exact and since losses are imputed to controllers, no insolvency should happen.

The code is incompatible with FoT tokens and those should never be used, the `TOLERANCE_CONSTANT` would be insufficient to protect against them and would lead to insolvencies. As such FoT tokens should never be used.

There are 2 types of tokens for which the `TOLERANCE_CONSTANT` could be necessary:
- stETH
- aTokens (or similar) Scaled tokens

stETH Edge Case

https://github.com/lidofinance/core/issues/442

aTokens Edge Case
We have investigated this edge case when working with Cap, for them it applies to their debt token so this would have no impact. However their code is very similar to AAVEs and I believe this finding would apply to you if you used aTokens as the `asset`

Repros:

Don't use tokens with underlying shares such as stETH or aTokens as assets

# A-04 Nuanced Risk that comes from Pricing via the Pricing Oracle - With emphasis on how to Safely Price ERC4626

## Executive Summary

Pricing a withdrawal of X assets with ERC4626.previewWithdraw can superficially seem correct.

However this will likely include the losses (expressed in shares) that are necessary in order for the withdrawal to happen.

This will lock a loss to the vault.

This loss should be imputed to the user.

In order to do so you have to price the ERC4626 while ignoring the losses that should be considered slippage.

### Pricing ERC4626 Safely even when the Vault is not compliant

- Convert
- Preview
- Execution

All 3 aspects have to be accounted for.

## Real examples

### Morpho - Standard

convertToShares uses the up to date assets:
https://github.com/morpho-org/metamorpho/blob/380bf7bfbc158bfb87150056d28c7a8688b642ef/src/MetaMorpho.sol#L631-L637

Therefore it will help establish the shares necessary to perform the withdrawal. (Rounded down)

From there you'd use that amount, since it's rounded down the controller will take a small loss. The Vault may have a small gain or no gain.

### Yearn - Not Standard wrt Losses

https://github.com/yearn/yearn-vaults-v3/blob/104a2b233bc6d43ba40720d68355b04d2dc31795/contracts/VaultV3.vy#L2084-L2102

`previewWithdraw` will convert the assets to shares rounding up.
You likely would rather use `convertToShares` and round down. As to not take the small rounding loss to the vault.

Actually withdrawing and redeeming can have sizeable losses.
You'd want to compute the assets that you will receive by simulating the operation offchain.

Only those assets (received by the amount of shares computed via `convertToShares`, should be given to the user. The vault should lock no loss at that point (at least at face value)

### Euler Earn - Not Standard wrt Gains

Euler earn has the gotcha that it will accrue assets on withdrawal, this can actually lead to receiving more assets per the shares.
Those excess assets should be kept in the SV instead of being attributed to the user.

As such you'd apply the same logic as with Morpho.
Then check the delta balance and return the min between the requested amount and the amount received.

### ERC7540 - Not Standard wrt both Losses and Gains

For ERC7540 you'd compute the shares necessary (convertToShares) at face value, rounding down (as to impute the small loss to the controller).

When claiming via withdraw (withdraw(maxWithdraw)), you'd then only grant the controller at most the assets they should have received at the older exchange rate (keep the yield in the SV), if any loss happened then the controller would receive even less.

# A-05 Superficial discussion on Risks and Complexities of PPS being determine by a group of validators

## Executive Summary

PPS update is subject to the following risks:
- N submitters pushing an invalid price
- Submitters needing to coordinate to reach a consensus on a price

### Determining if a price is valid

This in it of itself is not a solved issue as ultimately determining the right price (information) is a function of identifying the source more so than performing the computation necessary to achieve it.

Due to this, most often you are left with 2 options

#### Self guided discovery

Where price submitters identify sources autonomously, with the advantage that they can quickly adapt to new price sources and the downside being that it makes it more complex to validate whether the source is valid or acceptable

#### Hardcoded sources

Have the upside that verification can be mostly automated, the sources likely would be vetted and therefore could be more trusted. The clear downside is the continous need for updating the sources as well as needing to revalidate their reliability.

##### Hardcoded onchain sources

Provide an additional level of guarantees as we can use the value onchain thanks to storage proofs:
https://github.com/curvefi/storage-proofs (Not sure if audited)

The process of using these proofs has been discussed for years and works reliably, IIRC the only downside is needing to store each block blockhash to ensure proofs can then be referenced against that.

This would allow you to effectively prove all prices, and have a dispute process that is not based in game theory but rather in actual code.

Following the same reason, you can likely achieve gas savings (with the downside being computation complexity and risk of bugs) by using zkProofs to prove the storage values in aggregate.

#### Resolving Price Discrepancies

In lack of a fully provable process you likely will have to rely on game theory to provide some level of security.

Here's a few ideas:
- Identify aberrant prices through weighted mean -> Compute the mean for all prices (weight it based on trust / historical accuracy if you deem that useful), slash submitters that propose aberrant prices (requires the prices to be onchain)
- Select a proposer on each round -> Give more power to one or more proposers chosen at random (similar to how Ethereum works), they will have the ability to slash submitters
- Grant a centralized entity the ability to slash -> Puts all the power (and risk) onto one entity

# A-07 Collection of Operative Risks

## Executive Summary

This is a collection of risks that Vault Managers should be aware and plan around.

## Execute Hooks can cause losses (or gains) to the vault but won't automatically update the PPS

This means that there can be a delay between the totalAssets changing and the PPS reflecting that.

This will allow MEV actors an opportunity to arbitrage the discrepancy

Sufficiently high fees as well as batching rebalancing with price updates will prevent this.

## The Vault may be using a stale price

Due to blocks being full the oracle may not be updated in time resulting in leaking value

## Price updates may be frontrun to unfairly steal yield gains

Asynchronous vaults that allow synchronous operations carry the risk that actors can perform operations with new information while the oracle has yet to update.

A classic example is trying to frontrun a loss (mitigated by using the asynchronous flow for redemptions)

However for gains, the vault is gameable, all gains that are not vested in some way can likely be arbitraged by frontrunner

## The Execution of a withdrawal may be sandwiched to cause higher losses than intended

Some vaults may be rebasable, the admin should ensure that each fulfilled redemption receives some level of assets that is consistent with their offchain simulations

## Slippage tollerance should be paired with a record of losses to the VaultStrategy

Since the strategy can lose funds in performing a withdrawal, these losses should also be monitored by the manager.
Perhaps by adding a b4 / after check in their Multisig Scripts

## Order of Operation can create MEV opportunities for the Manager

Operating on the Vault consists of:
- Processing deposits (with a PPS and a Minting fee)
- Processing redemptions (with a zero or non zero slippage, depressed or over estimated pps)
- Investing / Divesting and Rebalancing Idle funds

Deposits are permissioneless but the update of the PPS is not.

Rebalancing may happen infrequently, but could also be done often, rebalancing itself could cause losses or small gains (although unlikely), and based on the pricing methodology (e.g. mark to market vs preview swap), could result in changing the PPS in both directions.

For similar reasons claiming rewards should lead to an increase in the PPS, but for technical reasons (slippage, poor execution, 2 quick PPS updates), this can also lead to PPS decreasing after auto-compounding rewards.

Redemptions carry many MEV opportunities, since redemptions could be fulfilled:
- With price that ignores rewards (increases PPS to the Vault)
- At PPS (causes only rounding error level changes to the PPS)
- With a gain to the redeemer (due to technical mistakes, causing a loss to the vault)

The combination of these opportunities for the manager gives them the ability to generally grant or withhold an update to the PPS worth of yield to actors interacting with the vault.

In extreme scenarios:
- Loss to the Vault
- Massive gain to the Vault

These can be significant.

Because of the preditability yet nuance of this MEV opportunities, my recommendation is that each manager explicitly state their "algorithm", they should provide a clear explanation as to how they would handle these (and emergency scenarios), as to provide clarity to what would happen.

It's worth noting that these MEV privileges are shares with ETF issuers, it may be worth reviewing how CeFi counterparties handle these scenarios, hopefully in a transparent way.

- The same price can now synchronously be used for deposits

And the opposite case
- A deposit is processed
- The price is slightly higher than intended to combat MEV at the deposit level
- The manager ignores this and fullfills redemptions
- The redemptions have leaked value from the SuperVault to the controllers

## Mitigation

Having a separate bid and ask, deposit and redeem prices, where deposits are overprice and redemptions are underpriced will mitigate this issue.

It will also avoid the need to have higher fees as to combat arbitrage.
